# Document Intelligence frontend

React + TypeScript operations console for the existing FastAPI backend. All
production screens use the real API. Synthetic data is isolated in src/test.

## Prerequisites

- Node.js 22.12+ or Node.js 24+, with npm. Prefer an installed supported LTS release.
- Backend migrations applied and API running.
- A separate invoice worker running with:

~~~powershell
python -m app.workers --processor app.services.invoice_pipeline:process_document --poll-seconds 2
~~~

The frontend cannot start a worker or recover a terminal failed job itself.

## Install and run (PowerShell, from frontend)

~~~powershell
node --version
npm --version
Copy-Item .env.example .env
npm install
npm run dev
~~~

Open http://127.0.0.1:5173. The example configuration uses VITE_API_BASE_URL=/.
The Vite development server forwards /api to DEV_API_PROXY_TARGET, which defaults
to http://127.0.0.1:8000. This development address is not embedded in client code.

Copy .env.example only when creating the local .env; preserve existing custom
configuration. Never commit .env. Commit the package-lock.json generated by npm
install, after reviewing and testing it. Subsequent installations should use npm ci.

## API contract

VITE_API_BASE_URL is the backend origin, without /api, or / for same-origin access.
The client validates successful responses using Zod schemas in src/contracts.ts.

- POST /api/documents/upload: repeated multipart files fields, HTTP 202.
- GET /api/documents: q, status, extension, offset, limit.
- GET /api/documents/{id}: metadata, job status, progress, and failure information.
- GET /api/documents/{id}/invoice: structured invoice and verified references.
- GET /api/documents/{id}/validation?extraction_id=...: current issues/duplicates.
- GET /api/documents/{id}/content: extraction_id, after_sequence, limit.

Content navigation carries the extraction ID returned by the backend. HTTP 409
causes a reload path instead of combining different processing attempts. No
single invoice view is assembled from different source-document IDs.

Amounts and quantities stay decimal strings. Display grouping uses string
operations, never binary floating-point arithmetic. Null is shown as Not provided.
Automated checks are never labeled human approval. Test-provider results have a
visible label. No analytics, progress values, confidence percentages, or invoice
values are fabricated in production.

Queries poll at four seconds for visible active work, and fifteen seconds for
other document/validation refreshes. Hidden tabs pause requests; transient read
failures back off. Upload POST requests are never automatically retried because
a lost response does not prove the server failed to accept the upload.

## Upload limits

Match these public settings to backend settings:

| Frontend | Backend |
| --- | --- |
| VITE_MAX_UPLOAD_FILES | MAX_UPLOAD_FILES |
| VITE_MAX_FILE_SIZE_MB | MAX_FILE_SIZE_MB |
| VITE_MAX_UPLOAD_TOTAL_MB | MAX_UPLOAD_TOTAL_MB |

Defaults are 10 files, 25 MiB/file, and 100 MiB/batch, matching the inspected
backend example. Server-side validation remains authoritative. These limits do
not disclose credentials. Never put GEMINI_API_KEY, DATABASE_URL, S3 credentials,
or authentication secrets in any VITE_ variable.

## Vercel and Railway integration

No backend source is modified by this package.

- Vercel project root: frontend.
- Build command: npm run build.
- Output directory: dist.
- Set VITE_API_BASE_URL to the actual HTTPS Railway API origin before building.
- Set public upload limits to match the deployed backend.
- Use the committed lockfile with npm ci in reproducible CI/deployment installs.
- Hash-based document routes work on static hosting without deep-link rewrites.
- The local Vite proxy is not part of the deployed dist output. A Vercel deployment
  with VITE_API_BASE_URL=/ needs an explicitly configured reverse proxy; otherwise
  set the real Railway origin.
- Loopback API origins are rejected by the production-build configuration.
- VITE_ variables are build-time configuration: rebuild after changes.

The backend already supports configurable CORS. Set CORS_ORIGINS to a JSON array
containing the exact Vercel frontend origin and any approved local origins. Avoid
wildcards. Existing GET/POST/OPTIONS methods and headers cover this UI. If using
direct backend URLs during local preview, include http://127.0.0.1:4173 as well.
Restart the backend after changing its environment.

The inspected backend has no authentication/reprocess/correction/comparison APIs.
Public-demo access protection remains a deployment task. This frontend adds no
client-side secret or fake authentication barrier. Use synthetic demonstration
documents. Missing backend capabilities are not represented by nonfunctional UI
buttons. Failed jobs can be resubmitted by uploading the original again; request
retry buttons only repeat reads.

## Troubleshooting

- Configuration required: copy .env.example to .env and restart Vite.
- Cannot reach API: check the API process, proxy target, HTTPS, and exact CORS origin.
- Invalid response: verify the deployed backend matches the supplied schemas.
- Queued indefinitely: start the independent invoice worker with its correct entry point.
- invoice_not_available: the document ran through the reading-only worker. Upload it
  again with the invoice worker running.
- extraction_changed: refresh the document to restart with its current version.
- Missing Gemini credentials: configure the backend/worker, then submit a new upload.
- Upload outcome uncertain: refresh the inbox before uploading again to avoid duplicates.
- PowerShell blocks npm.ps1: use npm.cmd for the same commands; do not weaken execution policy.
- Port conflict: stop the existing dev/preview process; strict ports prevent unnoticed CORS changes.
